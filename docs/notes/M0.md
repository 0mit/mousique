# M0 — spikes

## Verovio (held)

`spikes/verovio/` renders a hand-written MEI file with koron and sori on notes, a key signature mixing a flat and a koron, a grace note, a tie and an unmetered bar (`render.png`).

- Rendering: all of it draws correctly with Verovio 6.3.0; the log is empty.
- Our ids survive: every `xml:id` on a note, rest, chord and measure comes through into the SVG and the timemap. (An id on a `keySig` inside `staffDef` does not; nothing relies on it.)
- Timemap: shape confirmed and recorded in `DECISIONS.md`.
- Persian text: shaped and ordered correctly right-to-left in Chromium; the app still draws titles in HTML (see `DECISIONS.md`).
- The same checks now run on every `npm test` against MEI generated from the model, including a key change, a clef change, a meter change, chords with a sori and back-to-back triplets.

## Synth (held, measured; still needs a listen)

In headless Chromium the synth's oscillator frequencies were recorded while the demo phrase played: A koron (from the key signature) sounded at 427.47 Hz, which is 440 x 2^(-50/1200); B flat at 466.16 Hz; the tied B was not re-attacked; triplets and the riz repeated at the right rate for 72 per minute. What a measurement cannot say is whether the quarter tone sounds right to a player. The app has a button for exactly that: **Hear A · A koron · A · A sori**, using the score's own koron and sori sizes.

## OMR (run on two printed pages, by hand)

The operator supplied two photographed printed pages: a Mahur pish-daramad (Shahnazi) and the Pish-daramad
of Abu'ata from Ma'rufi's radif. No provider API key is configured on the development machine, so the app's
pipeline could not be exercised; instead the agent itself — a vision model of the kind the pipeline would
call — read one system from each page, cropped at twice the photo's size, into the score JSON, and the
result was rendered with the app's own pipeline and compared with the page.

- 11 bars, 45 notes and rests: no wrong pitches, no wrong durations, no missed accidentals. The Abu'ata key
  signature (B flat, E flat, A koron) was read correctly after enlarging it; at the photo's own size it is
  ambiguous.
- What could not be expressed was the model's limit, not the reading's: a slur (1), and fingering numbers
  below the staff (7). The `T` marks above were kept as text.
- Caveats, stated plainly: the reader also judged the result; both pages are clean print; no handwritten
  score was among the material (the handwritten page supplied is a rhythm chart, not a score). This shows
  that a draft *can* be right on clean print; it does not yet measure an error rate.

Recommendation: keep M5, and build it as the handover says (a crop per system, the strict JSON schema, the
validator, the review screen). Run the same comparison through the real pipeline once a key is configured,
and ask for a handwritten page before trusting it on handwriting.
